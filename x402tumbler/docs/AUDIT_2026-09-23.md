- **Project:** DarkCircle (`darkcircle/x402tumbler`): x402 payment privacy for Quai Network, WQUAI / WQI shielded pools
- **Date:** 2026-09-23
- **Scope:** `circuits/unshield.circom`, `contracts/DarkCirclePool.sol`, `contracts/DevToken.sol`, the Groth16
  verifier generated from them, and the application (`src/`, `ui/`, `scripts/`)

> **Read this first.** This assessment was carried out with an AI assistant inside the repository. Every claim
> in it is backed by a test or a reproduction, and every finding that could be fixed in code has been. It is

## 1. Executive summary

One **critical** soundness bug was found in the circuit: every note could be spent up to eight times. It was
proven on the compiled contracts (a 100-token note paid out twice from other depositors' funds), fixed in the
circuit and the executable specification, and the fix was proven by the same attack now failing. Keys,
verifier and contracts were rebuilt, and every future build now attempts this attack itself.

The x402 application had two **major** defects: a payment for a cheap resource unlocked an expensive one, and
expiry could strand a customer's payment by deleting the only key that reaches it. A medium one, found by a test
that failed only under load, could make a freshly shielded note permanently unspendable (APP-10).

### DCP-01 · A note has up to eight valid nullifiers (spending-key aliasing) · **Critical** · Resolved

**Location:** `circuits/unshield.circom` (C3), `src/sim/unshieldVerifier.ts` (C3/C4), `src/crypto/note.ts`

**Description.** Ownership (C3) is proven as `npk = Poseidon2((spendingKey * Base8).x, vpk.x)` and the nullifier
(C4) as `Poseidon3(spendingKey, commitment, leafIndex)`. `Base8` has order `L` (the BabyJubjub subgroup order,
about p/8), so `spendingKey` and `spendingKey + k·L` are the same public key and the same `npk`, and own the same
note, while each yields a different nullifier. The circuit accepted any `spendingKey < p` (`Num2Bits_strict`, 254
bits), which admits `k = 0 … 7`. The pool only checks that a nullifier is unused, so a depositor could withdraw
each note up to eight times and take the difference from everyone else's deposits. The simulation's
specification had the same flaw (public key from `key mod L`, nullifier from `key mod p`); the simulated pool
was only protected by an extra spent-commitment check that a private on-chain pool cannot perform.

**Proof of concept.** Against the compiled contracts on a local EVM (`@ethereumjs/evm`, the same bytecode): a
victim deposits 900 and the attacker 100; the attacker proves and submits an unshield of their note with `sk`,
then again with `sk + L`. Both proofs verified and both unshields were accepted: the recipient received 200 and
pool custody fell to 800. This is a known hazard of deriving a key with `EscalarMulFix`/`BabyPbk` over more bits
than the subgroup order; Semaphore v4, for example, constrains its identity secret below `L` for this reason.

**Recommendation.** Allow exactly one scalar per public key.

**Alleviation.** The circuit constrains `0 <= spendingKey < L` (`Num2Bits(251)` + `LessThan(251)` against `L`,
with `EscalarMulFix(251)`): 17,568 constraints, was 17,624. The executable specification refuses any key outside
`[0, L)` (`ERR_SPENDING_KEY_OUT_OF_RANGE`), and so does `Note.computeNullifier`. Keys, verifier and contracts
were rebuilt; the build's self-test and its local-EVM run (check E-13) now try `sk + L` with a consistent
nullifier every time, and the rebuilt circuit refuses it (the attack script now ends with the second spend
refused and the victim's 900 intact). Tests: the circuit's cheat list, `DCP-01` (unit).

### APP-01 · A paid invoice is not bound to the resource it was issued for · **Major** · Resolved

**Location:** `src/server/resourceServer.ts`, `src/gateway/gateway.ts` (`createMiddleware`)

**Description.** The resource server verified `(invoiceId, proof)` and served whatever route was asked for. An
invoice paid for `/api/v1/protected/analytics` (5 WQUAI) unlocked `/api/v1/protected/ai-inference` (10 WQUAI).
The middleware had the same gap and also minted one invoice per spelling of a query string.

**Alleviation.** Before verification, the invoice's `resourceUri` and token must match the route (403
`ERR_INVOICE_RESOURCE_MISMATCH` otherwise, with no side effect: the invoice stays unsettled). The middleware
binds the path without its query string. Tests: `APP-01` (3).

### APP-02 · Expiry un-settles payments, and pruning deletes the key to funded addresses · **Major** · Resolved

**Location:** `src/gateway/invoiceRegistry.ts`, `src/server/resourceServer.ts` (`StandaloneGateway`)

**Description.** Four paths, one outcome. (a) Re-presenting a settled but not yet swept invoice after its TTL (an
ordinary client retry) set its status to `EXPIRED`, and the sweeper only sweeps `SETTLED` invoices. (b) A payment
that landed in time but whose proof arrived after the TTL (normal with Quai confirmations) was refused. (c)
`pruneExpired` deleted every `EXPIRED` invoice at once, with no grace period, and capacity pruning (which
unauthenticated requests can trigger) deleted expired `PENDING` ones, whether or not their address held funds.
The invoice id is the only input besides the master key that derives the payee key, so pruning it strands the
customer's payment for good. (d) A settled invoice could be re-settled by a different transaction.

**Alleviation.** Settled and swept invoices never change status; after the TTL a re-presentation gets 410 and the
invoice stays sweepable. A `PENDING` invoice whose payment the ledger proves after the TTL is honoured, marked
`settledAfterExpiry` and swept as usual (the trusted-harness and demo gateways, which cannot prove anything,
keep the strict expiry). Pruning removes only an unpaid invoice past its grace period whose address the ledger
proves empty, and nothing at all when balances come from a live zone the registry cannot read. A second
transaction for a settled invoice gets 409 `ERR_INVOICE_ALREADY_SETTLED`. Tests: `APP-02` (5).

### DCP-02 · Payment bounds rely solely on the verifier's field checks · Medium · Resolved

`unshield` range-checked neither `amount` nor `fee` and depended on the snarkjs verifier's `checkField` for both.
The pool accepts any verifier address at deployment; with one that skips those checks, `fee + p` satisfies the
proof (the pairing and the Poseidon binding both reduce mod p) and `transfer(relayer, fee + p)` pays out far
more. **Alleviation:** the pool itself checks `0 < amount < 2^128` and `fee < 2^128` before the proof (local-EVM
check E-15, including `fee + p`).

### APP-03 · A destructive reset is enforced by the page only, and discarded saved state ages out · Medium · Resolved

`POST /api/reset` discarded every note, invoice and payee key with only a confirmation in the page. With
persistence on, the next few autosaves pushed the pre-reset snapshots out of the retention window (5 by default),
taking the payee keys of open invoices with them. **Alleviation:** the server requires `confirm: "RESET"`. With
persistence on it first saves the state it is about to discard and **pins** that snapshot: retention never
deletes a pinned snapshot, and it can be restored by number. Tests: `APP-03`, `reset pins the state it discards`.

### APP-10 · A clock tick during a shield can make the new note permanently unspendable · Medium · Resolved

**Location:** `src/actions/shield.ts`, `src/cli/context.ts`, `src/gateway/sweeper.ts`, `src/sim/railgunContract.ts`

The pool records a note's deposit time inside `shield()`, and compliance (PPOI) later requires the spender's copy
of the note to carry exactly that time. All three places that build the wallet's copy (a shield from the UI or
CLI, the initial treasury note, a swept payment) read the clock again after `shield()` returned. When a second
boundary fell between the two reads the copies disagreed, and every later spend of that note failed with
`PPOI_TIMESTAMP_MISMATCH`: an honest user's funds stuck with no way to fix it from the wallet. Rare (the reads
are microseconds apart) but more likely under load; it surfaced as one failure in 879 during a full run.
**Alleviation:** `shield()` returns the timestamp it recorded and every caller uses it. The regression test
forces the tick with a clock that advances on every read, and fails without the fix. Tests: `APP-10`.

### DCP-03 · A fee without a relayer, and payouts to the pool itself · Minor · Resolved

A proof with `fee > 0` and `relayer = 0` would burn the fee (or revert, depending on the token); `recipient` or
`relayer` equal to the pool would trap the payout. **Alleviation:** both are refused (E-15).

### DCP-04 · The constructor accepts dependencies without code · Minor · Resolved

An address without code answers every call with success and no data, so an EOA verifier or hasher leaves the pool
unusable. **Alleviation:** all four dependencies must have code (E-16).

### DCP-05 · ERC-20 calls assume a boolean return value · Minor · Resolved

Tokens that return nothing made every call revert on decoding. **Alleviation:** `_tokenCall` accepts `true` or no
return data (safe because the token's code was checked at construction) and refuses `false`, a revert or
malformed data.

### APP-04 · A malformed receipt log aborts payment verification · Minor · Resolved

`BigInt(log.data)` threw on anything but a hex word and failed the whole verification; a numeric status `1`
counted as a revert. **Alleviation:** logs that are not well-formed Transfers are skipped; `1`, `"1"` and `"0x1"`
mean success. Tests: `APP-04`.

### APP-05 · No graceful stop on SIGTERM; `--port` unchecked · Minor · Resolved

Only SIGINT flushed the pending autosave, so a service manager's SIGTERM lost the last changes.
**Alleviation:** both signals flush once; an invalid port is refused at start-up.

### APP-08 · Live payment verification defaults to one confirmation · Minor · Resolved

Reorgs of about 25 blocks have been seen on Orchard. **Alleviation:** with a live receipt source the gateway
defaults to 2 confirmations (still configurable). Tests: `APP-08`.

### DCP-06 · Floating pragma · Informational · Resolved

`^0.8.24` let a compiler change alter the bytecode that deployments are checked against. Pinned to `0.8.37` in
both contracts and in `package.json`.

### DCP-07 · `changeLeafIndex` is 0 both for "leaf 0" and "no change" · Informational · Resolved

The `Unshield` event reports `NO_LEAF` (`type(uint32).max`) when no change note was created (E-17).

### APP-06 · A `__proto__` key in a snapshot could re-parent a decoded object · Informational · Resolved

Snapshots are authenticated (AES-256-GCM), so only the key holder could craft one; the decoder now defines
properties instead of assigning them. Tests: `APP-06`.

### APP-07 · Swept notes are blinded with 128 random bits · Informational · Resolved

Not exploitable (2^128), but inconsistent with every other note; the sweeper now uses `Fp.random()`. Tests: `APP-07`.

### DCP-08 · Gas: storage-backed zero hashes and external Poseidon contracts · Informational · Acknowledged

Every insert reads 16 zero hashes from storage and makes 16 external Poseidon calls, and the circomlibjs hashers
are large (PoseidonT5 is 16,276 bytes). Measured on the local EVM: shield 1,047,458 gas, unshield 1,011,854 gas.
Deploying everything (both hashers, the verifier and both pools) is expected to cost roughly 1,300 to 1,650 QUAI
at the 2026-09-23 gas price (~35,000 gwei), about half of it PoseidonT5. A hand-optimised Poseidon and constant
zero hashes would cut all of these substantially; that is a new contract to audit, so it is left as a
recommendation.

### DCP-09 · No on-chain note-recovery data; 64-root window; no pause · Informational · Acknowledged

The pool emits no encrypted note data, so a recipient who loses the note (npk, value, rho) loses the funds;
proofs older than 64 insertions must be re-made; there is deliberately no owner, pause or upgrade path (`AUDIT.md`
O-16). These are design decisions for the team, not defects.

### APP-09 · One payment is an access pass for its TTL · Informational · Acknowledged

Re-presenting a paid invoice returns 200 until its TTL ends; the client's receipt cache relies on this. With
APP-01 fixed it only ever grants the resource that was paid for. If a payment must buy exactly one request, the
server needs a request identifier.

### DEP-01 · The pool deployment can never be verified or recorded · **Major** · Resolved

**Location:** `src/admin/deploy/chain.ts` (`verifyAndRecord`), `src/admin/deploy/contracts.ts`

`DarkCirclePool` has four `immutable` addresses. solc's `deployedBytecode` holds zero placeholders at 19 sites and
the constructor writes the real addresses there, so a real pool's on-chain code can never hash to the compiled
runtime hash, which is what the receipt check compared. Every real pool deployment would have ended in
`ERR_BYTECODE_MISMATCH` after its gas (about 250 QUAI) was spent, and could never be recorded or verified. The
tests missed it because their fake chain returned the compiled code itself. **Alleviation:** the compile stage
records each immutable's byte ranges by name (solc's `immutableReferences` joined with the AST); `bytecode.ts`
rebuilds the pool's exact runtime code from the token and the recorded verifier and hasher addresses, and the
receipt check compares hashes byte for byte, which also proves what the pool is bound to (a masked comparison
would have accepted a pool bound to the wrong verifier). The local-EVM stage (E-12) checks the reconstruction
against what a real EVM deployed. Tests: `DEP-01` (5).

### DEP-02 · Deployment transactions carry no access list and are not simulated · **Major** · Resolved

**Location:** `ui/admin/admin.js`, `ui/admin/wallet.js`, `src/admin/deploy/chain.ts`, `src/quai/rpc.ts`

On Cyprus-1 a transaction that touches more than one contract without an access list reverts and burns its
whole gas limit (11 such reverts were recorded on 2026-09-13). The pool's constructor calls PoseidonT3 sixteen
times, so its deployment is exactly such a transaction, and the wallet flow sent no list and simulated nothing.
A read-only probe on 2026-09-23 confirmed `quai_createAccessList` handles creations and lists a contract the
constructor calls. **Alleviation:** a `prepare` step (`/api/admin/deploy/chain/prepare`) rebuilds each step right
before signing and runs `quai_createAccessList` and `quai_estimateGas` (with the list) on the exact creation,
refusing any step the node says would fail; the list goes to `quai_sendTransaction`. `prepare` enforces the same
mainnet acknowledgement as preflight. Tests: `DEP-02` (3 unit, 2 route).

### DEP-03 · PoseidonT5's gas limit is below Quai's observed creation cost · **Major** · Resolved

Limits were 1,250 gas per byte. Creation has been charged about 2.5x `quai_estimateGas` on Cyprus-1 (16,025,454
used against a 6.5M estimate). PoseidonT5's live estimate is 9,095,088, so 2.5x is 22.7M, while its budget was
20.36M (2.2x). An out-of-gas creation burns the whole limit: about 712 QUAI at the 2026-09-23 gas price.
**Alleviation:** the limit is the larger of the size budget and **3x the live estimate**, capped below the block
gas limit (50M on Cyprus-1); a step whose cap leaves less than 2.5x is refused (`ERR_GAS_HEADROOM`). Preflight
prices every step it can already build from the same live simulation (so the balance it asks for is the one the
deployment needs; a size-based figure understated PoseidonT5 by a third), and refuses when the balance cannot
cover the largest step's whole gas limit, which a node requires before it accepts a transaction. On 2026-09-27
at ~28,800 gwei that meant about 1,190 QUAI for the shared contracts and one pool, and 786 QUAI of balance to
send PoseidonT5 at its full limit. Tests: `DEP-03` (4).

### DEP-04 · Poseidon hashers were recorded without any bytecode check · Medium · Resolved

circomlibjs ships the hashers as creation code only, so the receipt check recorded them with a warning and
accepted any code; a wrong hasher would then be bound into the pool. **Alleviation:** the compile stage runs their
creation code in a local EVM to get the runtime code, so every artifact carries a runtime hash and every
deployment is compared byte for byte; an artifact from an older build is refused (`ERR_ARTIFACT_OUTDATED`).

### DEP-05 · The receipt route trusts a client-chosen contract name · Medium · Resolved

The route took both `key` and `contract` from the request without relating them, so a verified deployment of
one contract could be recorded under another's key, and the name went unvalidated into a file path.
**Alleviation:** the key alone decides the contract; a disagreeing value is refused before any chain read, and
artifact names are validated.

### DEP-06 · The wallet's network and account are checked only at preflight · Medium · Resolved

The chain-id check used the value cached at preflight and was skipped when unknown. A network switch afterwards
could send an Orchard deployment to mainnet (bypassing the mainnet acknowledgement); because every Quai zone
shares chain id 9, an account switch could deploy into another zone. **Alleviation:** the page reads the wallet's
chain id and selected account immediately before each send and refuses any mismatch.

### DOC-01 · The console's documentation says no real-chain deploy path exists · Medium · Resolved

`docs/ADMIN_CONSOLE.md` still said there was no deploy button after the wallet-signed flow was added, so an
operator could not know which checks protect them. **Alleviation:** rewritten to describe the flow and each check.

### DEP-07 · A receipt's sender and kind are not checked · Minor · Resolved

The recorded deployer was whatever the request claimed. **Alleviation:** the receipt must come from the claimed
deployer and be a contract creation (`to` empty). Tests: `DEP-07`.

## 4. Centralisation and trust

The pool has no owner, pause or upgrade path, so there is no privileged account to compromise. It fully trusts
four addresses fixed at construction: the token, the verifier and the two hashers. Whoever deploys it chooses
them, so users must check a pool's bindings before trusting it (its code hash with the immutables filled in, or
its `token()`, `verifier()`, `hasher2()` and `hasher4()`). The proving key's trust is the ceremony's: whoever
controlled the single contributor's randomness can forge proofs and drain the pool.

| G-06 / O-1 | No independent audit of circuit, verifier and pool | This assessment is not one. |
| G-07 / O-14 | Compliance (PPOI, C8) is not in the circuit or contract | The pool cannot refuse a note from a sanctioned origin. |

deploying the contracts does not by itself give users a working product; key custody (O-4); constant-time
BabyJubjub (O-9).

## 6. Severity definitions

| Severity | Meaning here |
|---|---|
| Critical | Loses user funds or breaks the core guarantee, exploitable by any user. Must be fixed before anything is deployed. |
| Major | Loses funds or blocks the system under realistic conditions, or grants access that was not paid for. |
| Medium | Weakens a guarantee or defence in depth; loss needs an unusual condition or another bug. |
| Minor | Correctness or robustness issue with limited impact. |
| Informational | Style, best practice, gas, or a design decision worth recording. |
